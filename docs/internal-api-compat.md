# wanwan-client 兼容与异常处理规范 v0.3

## 1. 目标

本文件用于补充内部协议在长期使用中的兼容、异常处理、格式漂移、上游升级与演进规则。

目标：
- 上游厂商响应变化时，尽量不改主链路
- 新旧 provider 并存时，保证内部协议稳定
- 出现部分失败、格式不匹配、字段缺失时，能够明确标记并可定位

---

## 2. 兼容优先级

统一遵循以下优先级：

1. 保持内部协议稳定
2. 在适配层兼容外部变化
3. 非必要不改主链路阶段结构
4. 非必要不改外层 8 个字段
5. 破坏性升级必须显式升版本

---

## 3. 上游格式变化处理

### 3.1 新增字段
- 默认允许
- 不因上游多字段报错
- 有价值的新字段可后续映射进 `payload` / `meta`

### 3.2 缺失字段
- 若缺失关键字段，返回 `failed` 或 `partial`
- 必须写入：
  - `error.type = schema_mismatch` 或 `compat_error`
  - `error.retryable = false`（默认）
- 不得静默吞掉

### 3.3 字段类型变化
例如：
- 字符串变数组
- 对象变字符串
- 路径变 URL
- token usage 结构变化

处理原则：
- 先在适配层归一
- 可归一则继续
- 不可归一则返回结构化错误

### 3.4 字段改名
例如：
- `text` 改为 `content`
- `audio_url` 改为 `url`

处理原则：
- 在适配层统一映射
- 内部协议字段不跟着上游频繁改名

---

## 4. 异常处理分层

出现问题时优先按以下层次定位：

1. UI 层
2. 配置层
3. service/provider 适配层
4. 文件与资源引用层
5. 第三方服务层

内部协议必须尽量明确暴露“是哪一层出的问题”，不要把所有失败都写成模糊错误。

---

## 5. 错误码建议

建议统一采用：`[STAGE]_[CATEGORY]`

示例：
- `STT_TIMEOUT`
- `STT_SCHEMA_MISMATCH`
- `LLM_PROVIDER_UNAVAILABLE`
- `LLM_COMPAT_ERROR`
- `TTS_EMPTY_AUDIO`
- `RVC_MODEL_NOT_FOUND`
- `PLAYBACK_REF_INVALID`

要求：
- `code` 稳定、可检索、可统计
- 不使用临时随意字符串

---

## 6. 降级规则

长期协议必须允许降级，不得把所有异常都视为整条链路失败。

典型降级示例：
- `rvc` 失败 → 直接使用 `tts` 音频，`status = degraded`
- `tts` 失败 → 保留 `llm.reply_text`，交给 UI 文本查看
- `stt` 部分成功 → 返回 `partial` 与已有文本

降级时要求：
- `status = degraded`
- `meta.degraded_from` 必填
- `error` 说明原始失败原因
- `payload.output` 仍提供可用替代结果

---

## 7. 流式与部分结果

即使当前 MVP 暂不主做流式，也必须保留协议兼容性。

建议：
- 中间态使用 `running`
- 分段可用结果使用 `partial`
- `stt.segments`、`llm.reply_message`、`playback.played` 等字段允许逐步填充
- 不因当前版本未实现流式而删除相关状态入口

---

## 8. 资源引用兼容规则

资源引用统一优先使用 ref 对象，而不是裸路径。

若旧实现仍是：
- `input_audio_path`
- `output_audio_path`
- `audio_url`

适配方式：
- 在阶段入口统一转成 `audio_ref`
- 在阶段出口统一输出 `audio_ref` 或 `playable_ref`

不得在主链路各处混用多套路径字段。

---

## 9. 版本管理

### 9.1 协议版本
当前协议版本：`v0.3`

### 9.2 向后兼容
允许：
- 新增 `payload` 内字段
- 新增 `meta` 内字段
- 新增 `error.details` 子字段

不建议：
- 修改外层 8 字段名称
- 删除既有最小必填结果
- 更改 status 枚举含义

### 9.3 破坏性升级
若必须破坏性变更：
1. 提升协议版本号
2. 提供迁移说明
3. 在适配层保留一段过渡兼容逻辑
4. 不直接把旧实现全部打废

---

## 10. 自检清单

新增或修改任一阶段实现后，至少自检：

1. 是否仍遵循外层 8 字段
2. 是否输出最小可用结果
3. 是否能区分 success / failed / partial / degraded / skipped
4. 是否通过适配层而不是主链路直接消费第三方原始响应
5. 是否在错误时给出结构化 `error`
6. 是否保留 `trace_id` 贯穿全链路
7. 是否支持资源引用而不是只支持本地路径
8. 是否在上游字段变动时可局部兼容

---

## 11. 结论

长期可用的关键不是“把所有厂商字段都写进协议”，而是：
- 保持内部协议稳定
- 把不稳定留给适配层
- 把异常显式结构化
- 把资源表达抽象成引用
- 把阶段最小结果定义清楚

wanwan-client 的长期稳定性，应优先建立在这套原则上，而不是建立在某一家厂商当前字段长什么样。
