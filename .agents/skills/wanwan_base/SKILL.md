# wanwan_base

## 项目背景
你正在参与一个名为 `wanwan-client` 的项目开发。

项目目标：
- 当前阶段：先做 Windows 客户端
- 后续阶段：支持 Android 客户端
- 架构原则：Windows-first, Android-ready
- 当前重点：先完成可运行的 Windows MVP，不提前为 Android 做过度设计

当前优先级：
文本聊天 > TTS > 录音 > STT 回填 > 自动播报

当前不优先处理：
- 实时双工语音
- 流式 RVC
- 回声消除
- 大规模跨平台重构
- 为 Android 提前重写架构

---

## 目录约定
主代码目录：

- `src/wanwan_client/core/`：平台无关核心业务逻辑
- `src/wanwan_client/services/`：外部服务接入封装（LLM / TTS / STT / RVC 等）
- `src/wanwan_client/infrastructure/`：基础设施能力（http、文件、日志、设置等）
- `src/wanwan_client/desktop/`：Windows 客户端当前界面与交互
- `src/wanwan_client/shared/`：共享常量、工具、数据结构

其他目录：

- `data/`：运行数据（角色、会话、配置、缓存、临时文件）
- `logs/`：日志
- `tests/`：测试代码与测试记录
- `assets/`：静态资源
- `scripts/`：开发脚本、启动脚本

规则：
- 不把平台相关逻辑写进 `core/`、`services/`
- 不把业务逻辑塞进 `desktop` 页面脚本
- 不新增无关顶层目录
- 不创建平行实现和重复模块

## 命名规范
统一使用以下命名规则：

- 目录名：`snake_case`
- 文件名：`snake_case`
- Python 类名：`PascalCase`
- 函数名：`snake_case`
- 变量名：`snake_case`
- 常量名：`UPPER_SNAKE_CASE`

禁止使用混乱命名，例如：
- `final_v2`
- `new_new`
- `temp2`
- `backup_final`
- `test_final_ok`

文件、类、函数命名应清晰表达职责，不使用模糊词。

## 工作流程
执行任何任务时，默认遵循以下流程：

1. 先理解当前目标和上下文
2. 先阅读相关目录和相关文件
3. 明确本次只改哪些文件
4. 小步修改，不做整仓重构
5. 改完后说明：
   - 改了什么
   - 为什么这样改
   - 有什么风险
   - 验证方式是什么
   - 下一步建议是什么

如果任务边界不清：
- 先收敛目标
- 不擅自扩展需求
- 不顺手修改无关模块

- 改动说明
- 风险点
- 验收方式
- 下一步建议

## 代码注释与解释规则
当前项目处于开发早期，代码输出默认应兼顾“可运行”和“可理解”。

在编写或修改代码时，必须遵守以下规则：

1. 默认按适合初学者阅读的方式写代码
2. 不允许只输出纯代码而不解释
3. 每个主要逻辑块前必须添加中文注释
4. 每个主要逻辑块结束后，应用中文补充说明该段代码的作用
5. 注释应解释“这段代码为什么存在、在当前页面或当前链路里起什么作用”
6. 不要求每一行都注释，但必须按逻辑块进行分段注释
7. HTML、JavaScript、Python 均适用该规则
8. 对于页面文件，应说明每个主要区域的作用
9. 对于 JavaScript，应说明事件绑定、状态变量、函数调用链路
10. 对于 Python，应说明入口函数、核心类、关键方法、配置读取、服务调用和返回值处理

代码输出后，必须额外提供“分段解释”，至少包括：
- 改了哪些文件
- 每个文件新增或修改了哪些逻辑块
- 每个逻辑块的作用是什么
- 当前最值得重点理解的几行或几段代码
- 这段代码运行后，页面或功能会发生什么变化

除非用户明确要求只给代码，否则不得只输出纯代码。

## 硬性规则
必须遵守以下规则：

1. 不进行无授权的大规模重构
2. 不修改与当前任务无关的文件
3. 不新增无意义的临时文件、重复文件、备份文件
4. 不把 API Key、绝对本机路径、敏感配置硬编码进源码
5. 不把测试代码混进正式业务目录
6. 不为了“更优雅”而推翻已可运行代码
7. 优先保证代码可运行、可验证、可回退
8. 平台无关逻辑必须保持可迁移，方便后续 Android 接入
9. 当前阶段优先完成 Windows MVP，不提前引入复杂跨平台框架
10. 如需新增文件，必须文件职责单一、命名清晰、放置位置正确
